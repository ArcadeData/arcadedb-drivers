# Adopting the 26.10.1 contract and closing the driver gap

**Status:** design approved, plan pending
**Date:** 2026-09-11
**Contract:** `26.9.1` → `26.10.1-SNAPSHOT`
**Upstream:** ArcadeData/arcadedb#7305, #7306, #7308, #7309, #7310, #7311
**Supersedes nothing.** Extends the M1/M1b/M3/M3b client designs rather than reworking them.

> **This is a dated design record.** The milestone boundaries and the decisions in §3 are the
> contract between this document and the issues filed from it; the measured figures in §2 were
> taken against `origin/chore/contract-refresh` on 2026-09-11 and will drift as the SNAPSHOT
> moves. That drift is expected and is not something to chase — §7 says what to do about it.

## 1. Scope

Four published packages — `@arcadedb/driver`, `@arcadedb/driver-grpc`, `arcadedb-driver`,
`arcadedb-driver-grpc` — are generated from a contract that is now one server version behind. The
new contract is not a refresh: it carries the client-facing result of six closed ArcadeDB issues,
and it breaks the TypeScript build.

This document covers adopting that contract and deciding, per capability, what "the drivers cover
it" means. It does not redesign any client's existing public surface.

## 2. What actually changed

### 2.1 OpenAPI — 64 → 69 paths

| Added | Why |
|---|---|
| `POST /api/v1/vector/{database}/search` | arcadedb#7306 |
| `POST /api/v1/vector/{database}/hybrid` | arcadedb#7306 |
| `POST /api/v1/vector/{database}/fulltext` | arcadedb#7306 |
| `POST /api/v1/cluster/auth-session` | cluster control plane |
| `POST /api/v1/cluster/capabilities` | cluster control plane |

Nothing was removed. The consequential change is not a new path at all: `POST /api/v1/query`,
`GET /api/v1/query/{language}/{command}`, `POST /api/v1/command` and `POST /api/v1/batch` each
gained an `Accept` header parameter and a second `200` media type, `application/x-ndjson`
(arcadedb#7306 for query and command, arcadedb#7311 for batch). `/batch` additionally gained
seventeen tuning query parameters.

All three vector endpoints are JSON in, JSON out. Neither generator skips them.

### 2.2 Proto — 23 → 65 RPCs, 702 → 1678 lines

Nothing was removed. Grouped by what a client would do with them:

- **Data plane, unary:** `VectorSearch`, `HybridSearch`, `FullTextSearch` (arcadedb#7306),
  `TimeSeriesWrite`, `TimeSeriesLatest` (arcadedb#7305)
- **Data plane, streaming:** `TimeSeriesWriteStream` (client-streaming),
  `TimeSeriesQuery` (server-streaming) — both arcadedb#7305
- **Control plane, streaming:** `RestoreBackup`, `RestoreDatabase`, `ImportDatabase`
  (arcadedb#7308) — server-streaming precisely so a long restore reports progress and stays
  cancellable
- **Control plane, unary (32 RPCs):** `OpenDatabase`, `CloseDatabase`, `AlignDatabase`,
  `GetProgress` and `ListSessions` (arcadedb#7310), `UpdateUser`, `ListUsers`, `ListGroups`,
  `SaveGroup`, `DeleteGroup`, `ListApiTokens`, `CreateApiToken`, `DeleteApiToken`
  (arcadedb#7309), `SetServerSetting`, `SetDatabaseSetting`, `GetBackupConfig`,
  `SetBackupConfig`, `ListBackups`, `TriggerBackup`, `DeleteBackup`, the six `Profiler*` RPCs,
  `GetServerEvents`, `Shutdown`, `ConnectCluster`, `DisconnectCluster`, `Health`, `Ready`

### 2.3 The one thing that is broken

`typescript/packages/driver/src/facade/data.ts:114` and `:136` fail to typecheck:

```
error TS2345: Argument of type '{ error?: …; record?: …; stats?: … } | { … }'
  is not assignable to parameter of type '{ limit?; result?; returned?; truncated? }'.
```

`openapi-typescript` unions every media type declared under a response code, so the `200` for
query and command is now *the JSON envelope* or *one ndjson item* (`{error?, record?, stats?}`).
`toEnvelope` still expects only the first. Python is unaffected because
`openapi-python-client` models the alternatives differently.

This is the whole of the TypeScript failure reported by `contract-watch.yml` on PR #31. There is
no behaviour regression hiding behind it.

## 3. Decisions

| # | Decision | Choice |
|---|---|---|
| D1 | Decomposition | Adoption first as its own milestone, then one milestone per capability |
| D2 | Contract target | Adopt `26.10.1-SNAPSHOT` now; a later mechanical PR adopts released `26.10.1` |
| D3 | Publishing | Nothing is published from a SNAPSHOT server version |
| D4 | Parity bar | Facade the data plane and every streaming RPC; unary control-plane RPCs stay raw-only and documented |
| D5 | HTTP streaming | Its own milestone, hand-written transport beside the generated client |
| D6 | The ndjson union | M4 narrows it at the type level only; M7 turns the narrowing into a real discriminator |

**D1** keeps a red bot PR from blocking four independent features, and keeps each capability's
review small enough to be a real review.

**D2** follows the precedent already in this repository's history: PRs #10, #11 and #13 tracked
`26.9.1-SNAPSHOT` and #23 adopted the release. The alternative — waiting — blocks every milestone
below on an external release date for no gain.

**D4** is the one decision worth defending. Today only three gRPC RPCs are reachable solely
through `raw` (`BulkInsert`, `InsertBidirectional`, `GraphBatchLoad`), so "everything gets a
facade" is close to the current rule. Forty-two new RPCs changes what that rule costs: full parity
across both languages, sync and async, is on the order of 170 hand-written methods and as many
tests, for a control plane most driver users never touch. The bar instead tracks what a facade
actually buys. A streaming RPC is hard to call correctly against a bare stub — that is why
`stream_query` and `insert_stream` are wrapped — and a data-plane call belongs in the object the
user already has. A unary admin RPC is a one-line stub call whose facade would add a name and
nothing else.

## 4. Milestones

### M4 — Adopt `26.10.1-SNAPSHOT`

**No new hand-written public surface** — no new facade method, option, error type or exported
helper is written by hand in M4. That is not the same as "no new published API", and the
distinction matters for semver: `typescript/packages/driver-grpc/src/index.ts` carries a
pre-existing `export * from "./gen/arcadedb-server-<version>_pb.js"`, so regenerating from the new
contract re-exports every message type, enum and schema backing all 42 new RPCs straight out of
the package entry point. That is a **minor** version bump's worth of surface expansion arriving as
a side effect of a regeneration, intended and unavoidable given the wildcard, and it lands with no
hand-written line to review. The Python gRPC package widens the same way, if less bluntly: it
exports no wildcard, but `messages` (the whole generated `arcadedb_server_pb2` module) is in its
`__all__`, so the new message types arrive namespaced under `messages.` rather than flattened into
the top level.

The deliverable is four packages green against `arcadedata/arcadedb:26.10.1-SNAPSHOT`.

`contract-watch.yml` force-pushes `chore/contract-refresh` in place every day, so this work cannot
live on that branch. M4 is a human branch; merging it closes PR #31 and drivers#21.

1. `scripts/fetch-contract.sh` both contracts, then
   `scripts/adopt-contract-version.sh 26.10.1-SNAPSHOT`. The script needs no change — its
   `LANGUAGES` table is unaffected.
2. Fix `facade/data.ts`. The driver sends no `Accept: application/x-ndjson` in M4, so the ndjson
   branch of the union is unreachable at runtime. The fix is a named narrowing helper carrying a
   comment that says exactly that, not a cast inlined into the `toEnvelope` call — M7 replaces the
   helper's body with a real discriminator and the comment is what tells the next reader so.
3. Regenerate both gRPC packages. Forty-two RPCs appear on the stub and on `raw`; no facade
   changes, no README claims about them yet.
4. Re-run `python/scripts/check_codegen_skips.py` and require the skip set to come back
   **unchanged** — the same four operations. `/batch` gained an `Accept` header and seventeen
   query parameters but its request body is still `application/jsonl`, `application/x-ndjson` or
   `text/csv`, so it must still skip; `ts/write` is untouched. A moved skip set is a stop-and-look,
   never a widened allowlist.
5. Add the compatibility-table row to each of the four READMEs. Root `CLAUDE.md` makes this a human
   decision, and this is the human making it.

**Verification:** both CI workflows green, and e2e for both languages against the SNAPSHOT image.

**Out of scope:** any use of the ndjson media type, the vector endpoints, the cluster endpoints, or
any new RPC.

### M5 — Vector search (arcadedb#7306, vector half)

The cheapest real feature: three JSON-in/JSON-out endpoints that both generators already emit.

- **HTTP:** a `vector` facade namespace with `search`, `hybrid` and `fulltext`, shaped like the
  existing `timeseries` namespace — TypeScript synchronous, Python synchronous plus its `Async`
  twin, per that workspace's deliberate hand-maintained duplication.
- **gRPC:** `VectorSearch`, `HybridSearch` and `FullTextSearch` are unary but data-plane, so they
  get facade methods, and they pass through `TransactionHandle._bind` wherever a database or
  transaction applies — the same override that makes transaction hijack unrepeatable through the
  handle.
- **Prose:** `efSearch` and result-limit bounds are validated server-side. The READMEs must say the
  clients do not pre-validate them, so a caller knows where a rejection comes from.

### M6 — Time series over gRPC (arcadedb#7305)

- `TimeSeriesWriteStream` is client-streaming: mirror `insert_stream` / `createInsertStream`.
- `TimeSeriesQuery` is server-streaming: mirror `stream_query` / `createStreamQuery`.
- `TimeSeriesWrite` and `TimeSeriesLatest` are unary data-plane facade methods.

This milestone also reaches a gap that predates the contract bump. `POST /ts/{database}/write`
takes a `text/plain` line-protocol body, `openapi-python-client` skips it, and it is one of the
four pinned entries in `EXPECTED_SKIPS` — so `arcadedb-driver` can read time series over HTTP and
cannot write it. gRPC `TimeSeriesWrite` gives Python a typed write path without hand-writing an
HTTP transport for it.

**Open question for M6's own spec:** does that retire the HTTP gap, or is a hand-written
`ts/write` still wanted for users who are not taking a gRPC dependency? Decide it there, with the
answer written into `python/CLAUDE.md` either way.

### M7 — HTTP ndjson streaming (arcadedb#7306 streaming half, arcadedb#7311)

Neither generated layer can express this: `openapi-fetch` buffers the response and
`openapi-python-client` parses it whole. So a small hand-written streaming path sits *beside* the
generated client and shares its base URL, its auth and its error mapping — sharing those is the
requirement, because two ways to authenticate or to raise is the defect this milestone is most
likely to introduce.

- TypeScript: `fetch` plus `ReadableStream`, surfaced as an `AsyncIterable`.
- Python: `httpx.stream` with `iter_lines`, synchronous and asynchronous.
- Surface: `queryStream` / `commandStream`, `query_stream` / `command_stream`.
- Then streaming `/batch`, which per arcadedb#7311 stays `Accept`-negotiated so the unary response
  shape is byte-identical for a caller that does not ask for the stream.

M4's D6 narrowing helper becomes the real discriminator here.

### M8 — Control plane, raw-only and documented (arcadedb#7308, #7309, #7310)

No new facade code, with two candidate exceptions. The deliverable is a README section in each
gRPC package enumerating the thirty-two unary admin RPCs and the three server-streaming
restore/import RPCs as reachable on `raw` / the stub, in the same voice the existing READMEs use
for `BulkInsert` and `GraphBatchLoad`.

(Counted from the committed `.proto`: 65 RPCs in total against 23 before, so 42 are new — 5 unary
data plane, 2 streaming data plane, 3 control-plane streaming, and the remaining 32 control-plane
unary. §2.2 said "25" for that last group while enumerating 32 of them; the enumeration was
right.)

Two things this milestone must decide rather than assume:

1. **`CreateApiToken` returns secret material.** arcadedb#7309 makes the server-side argument that
   a token-bearing response must be proved not to reach a log sink. The client side needs the same
   proof: that no interceptor or middleware in either facade touches a response body, and a README
   line saying so. If any does, that is a finding, not a documentation task.
2. **`Health` and `Ready`** are trivial, useful, and the most likely thing an operator calls from a
   driver. They may be the one pair worth facading despite D4.

## 6. Tracking

One issue per milestone, labelled from the repository's existing vocabulary (`contract`,
`codegen`, `http-driver`, `grpc-driver`, `typescript`, `python`, `e2e`), collected under a single
GitHub milestone for the release that carries them. The classifier in `classify-issue.yml` can only
choose from labels that already exist, so no new label is introduced for this work.

## 7. Risks

**The SNAPSHOT moves daily.** M4 may need a re-fetch before it merges. The mitigation is to merge
M4 quickly rather than to pin anything: once it is in, `contract-watch.yml` resumes against the
adopted version and any further movement is reported the normal way.

**A widened skip set would pass unnoticed.** This is the failure mode `check_codegen_skips.py`
exists for, and M4 step 4 is the only place in this plan where the right response to a green-ish
signal is to stop. Called out here so it is not treated as a formality.

**Two ways to call the server.** M7 introduces a second HTTP path. If it grows its own auth or its
own error type, the driver has two contracts with its users. The design constraint in M7 is not
decoration.
