# Adopting the 26.10.1 contract and closing the driver gap

**Status:** design approved, plan pending
**Date:** 2026-09-11
**Contract:** `26.9.1` → `26.10.1-SNAPSHOT`
**Upstream:** ArcadeData/arcadedb#7305, #7306, #7308, #7309, #7310, #7311
**Supersedes nothing.** Extends the M1/M1b/M3/M3b client designs rather than reworking them.

> **This is a dated design record.** The milestone boundaries and the decisions in §3 are the
> contract between this document and the issues filed from it; the measured figures in §2 were
> taken against `origin/chore/contract-refresh` on 2026-09-11 and will drift as the SNAPSHOT
> moves. That drift is expected and is not something to chase — §7 says what to do about it.

## 1. Scope

Four published packages — `@arcadedb/driver`, `@arcadedb/driver-grpc`, `arcadedb-driver`,
`arcadedb-driver-grpc` — are generated from a contract that is now one server version behind. The
new contract is not a refresh: it carries the client-facing result of six closed ArcadeDB issues,
and it breaks the TypeScript build.

This document covers adopting that contract and deciding, per capability, what "the drivers cover
it" means. It does not redesign any client's existing public surface.

## 2. What actually changed

### 2.1 OpenAPI — 64 → 69 paths

| Added | Why |
|---|---|
| `POST /api/v1/vector/{database}/search` | arcadedb#7306 |
| `POST /api/v1/vector/{database}/hybrid` | arcadedb#7306 |
| `POST /api/v1/vector/{database}/fulltext` | arcadedb#7306 |
| `POST /api/v1/cluster/auth-session` | cluster control plane |
| `POST /api/v1/cluster/capabilities` | cluster control plane |

Nothing was removed. The consequential change is not a new path at all: `POST /api/v1/query`,
`GET /api/v1/query/{language}/{command}`, `POST /api/v1/command` and `POST /api/v1/batch` each
gained an `Accept` header parameter and a second `200` media type, `application/x-ndjson`
(arcadedb#7306 for query and command, arcadedb#7311 for batch). `/batch` additionally gained
seventeen tuning query parameters.

All three vector endpoints are JSON in, JSON out. Neither generator skips them.

### 2.2 Proto — 23 → 65 RPCs, 702 → 1678 lines

Nothing was removed. Grouped by what a client would do with them:

- **Data plane, unary:** `VectorSearch`, `HybridSearch`, `FullTextSearch` (arcadedb#7306),
  `TimeSeriesWrite`, `TimeSeriesLatest` (arcadedb#7305)
- **Data plane, streaming:** `TimeSeriesWriteStream` (client-streaming),
  `TimeSeriesQuery` (server-streaming) — both arcadedb#7305
- **Control plane, streaming:** `RestoreBackup`, `RestoreDatabase`, `ImportDatabase`
  (arcadedb#7308) — server-streaming precisely so a long restore reports progress and stays
  cancellable
- **Control plane, unary (32 RPCs):** `OpenDatabase`, `CloseDatabase`, `AlignDatabase`,
  `GetProgress` and `ListSessions` (arcadedb#7310), `UpdateUser`, `ListUsers`, `ListGroups`,
  `SaveGroup`, `DeleteGroup`, `ListApiTokens`, `CreateApiToken`, `DeleteApiToken`
  (arcadedb#7309), `SetServerSetting`, `SetDatabaseSetting`, `GetBackupConfig`,
  `SetBackupConfig`, `ListBackups`, `TriggerBackup`, `DeleteBackup`, the six `Profiler*` RPCs,
  `GetServerEvents`, `Shutdown`, `ConnectCluster`, `DisconnectCluster`, `Health`, `Ready`

### 2.3 The one thing that is broken

`typescript/packages/driver/src/facade/data.ts:114` and `:136` fail to typecheck:

```
error TS2345: Argument of type '{ error?: …; record?: …; stats?: … } | { … }'
  is not assignable to parameter of type '{ limit?; result?; returned?; truncated? }'.
```

`openapi-typescript` unions every media type declared under a response code, so the `200` for
query and command is now *the JSON envelope* or *one ndjson item* (`{error?, record?, stats?}`).
`toEnvelope` still expects only the first. Python is unaffected because
`openapi-python-client` models the alternatives differently.

This is the whole of the TypeScript failure reported by `contract-watch.yml` on PR #31. There is
no behaviour regression hiding behind it.

## 3. Decisions

| # | Decision | Choice |
|---|---|---|
| D1 | Decomposition | Adoption first as its own milestone, then one milestone per capability |
| D2 | Contract target | Adopt `26.10.1-SNAPSHOT` now; a later mechanical PR adopts released `26.10.1` |
| D3 | Publishing | Nothing is published from a SNAPSHOT server version |
| D4 | Parity bar | Facade the data plane and every streaming RPC; unary control-plane RPCs get no facade — only a generated stub handle — and are documented |
| D5 | HTTP streaming | Its own milestone, riding the generated client in both languages rather than a transport beside it |
| D6 | The ndjson union | M4 narrows it at the type level only; M7 turns the narrowing into a real discriminator |

**D1** keeps a red bot PR from blocking four independent features, and keeps each capability's
review small enough to be a real review.

**D2** follows the precedent already in this repository's history: PRs #10, #11 and #13 tracked
`26.9.1-SNAPSHOT` and #23 adopted the release. The alternative — waiting — blocks every milestone
below on an external release date for no gain.

**D4** is the one decision worth defending. Today only three gRPC RPCs are reachable solely
through `raw` (`BulkInsert`, `InsertBidirectional`, `GraphBatchLoad`), so "everything gets a
facade" is close to the current rule. Forty-two new RPCs changes what that rule costs: full parity
across both languages, sync and async, is on the order of 170 hand-written methods and as many
tests, for a control plane most driver users never touch. The bar instead tracks what a facade
actually buys. A streaming RPC is hard to call correctly against a bare stub — that is why
`stream_query` and `insert_stream` are wrapped — and a data-plane call belongs in the object the
user already has. A unary admin RPC is a one-line call against whatever generated stub exposes
it — `raw` covers the data plane; the admin service needs its own handle — so a facade would add a
name and nothing else.

## 4. Milestones

### M4 — Adopt `26.10.1-SNAPSHOT`

**No new hand-written public surface** — no new facade method, option, error type or exported
helper is written by hand in M4. That is not the same as "no new published API", and the
distinction matters for semver: `typescript/packages/driver-grpc/src/index.ts` carries a
pre-existing `export * from "./gen/arcadedb-server-<version>_pb.js"`, so regenerating from the new
contract re-exports every message type, enum and schema backing all 42 new RPCs straight out of
the package entry point. That is a **minor** version bump's worth of surface expansion arriving as
a side effect of a regeneration, intended and unavoidable given the wildcard, and it lands with no
hand-written line to review. The Python gRPC package widens the same way, if less bluntly: it
exports no wildcard, but `messages` (the whole generated `arcadedb_server_pb2` module) is in its
`__all__`, so the new message types arrive namespaced under `messages.` rather than flattened into
the top level.

The deliverable is four packages green against `arcadedata/arcadedb:26.10.1-SNAPSHOT`.

`contract-watch.yml` force-pushes `chore/contract-refresh` in place every day, so this work cannot
live on that branch. M4 is a human branch; merging it closes PR #31 and drivers#21.

1. `scripts/fetch-contract.sh` both contracts, then
   `scripts/adopt-contract-version.sh 26.10.1-SNAPSHOT`. The script needs no change — its
   `LANGUAGES` table is unaffected.
2. Fix `facade/data.ts`. The driver sends no `Accept: application/x-ndjson` in M4, so the ndjson
   branch of the union is unreachable at runtime. The fix is a named narrowing helper carrying a
   comment that says exactly that, not a cast inlined into the `toEnvelope` call — M7 replaces the
   helper's body with a real discriminator and the comment is what tells the next reader so.
3. Regenerate both gRPC packages. The seven new data-plane RPCs (`VectorSearch`, `HybridSearch`,
   `FullTextSearch`, `TimeSeriesWrite`, `TimeSeriesLatest`, `TimeSeriesWriteStream`,
   `TimeSeriesQuery`) land on `raw`, like every other `ArcadeDbService` RPC. The other 35 — the new
   `ArcadeDbAdminService` RPCs — land only on the generated stub class; nothing in either package
   exposes that class yet, so they are not reachable at the end of M4 (see §4 M8). No facade
   changes, no README claims about any of them.
4. Re-run `python/scripts/check_codegen_skips.py` and require the skip set to come back
   **unchanged** — the same four operations. `/batch` gained an `Accept` header and seventeen
   query parameters but its request body is still `application/jsonl`, `application/x-ndjson` or
   `text/csv`, so it must still skip; `ts/write` is untouched. A moved skip set is a stop-and-look,
   never a widened allowlist.
5. Add the compatibility-table row to each of the four READMEs. Root `CLAUDE.md` makes this a human
   decision, and this is the human making it.

**Verification:** both CI workflows green, and e2e for both languages against the SNAPSHOT image.

**Out of scope:** any use of the ndjson media type, the vector endpoints, the cluster endpoints, or
any new RPC.

### M5 — Vector search (arcadedb#7306, vector half)

The cheapest real feature: three JSON-in/JSON-out endpoints that both generators already emit.

- **HTTP:** a `vector` facade namespace with `search`, `hybrid` and `fulltext`, shaped like the
  existing `timeseries` namespace — TypeScript synchronous, Python synchronous plus its `Async`
  twin, per that workspace's deliberate hand-maintained duplication.
- **gRPC:** `VectorSearch`, `HybridSearch` and `FullTextSearch` are unary but data-plane, so they
  get facade methods, and they pass through `TransactionHandle._bind` wherever a database or
  transaction applies — the same override that makes transaction hijack unrepeatable through the
  handle.
- **Prose:** `efSearch` and result-limit bounds are validated server-side. The READMEs must say the
  clients do not pre-validate them, so a caller knows where a rejection comes from.

### M6 — Time series over gRPC (arcadedb#7305)

> **Corrected 2026-09-12** (`ArcadeData/arcadedb-drivers#38`): this section originally claimed
> `arcadedb-driver` could read time series over HTTP but not write it, and posed an open question
> about whether gRPC `TimeSeriesWrite` would retire that gap. Both halves were wrong — the HTTP
> write path already exists, hand-written, in both languages. The section below replaces the
> original text rather than annotating it; see the M6 plan and issue #38 for how the error was
> found.

Four RPCs, each treated per the parity rule established in §4 M5 (wrap what a bare stub drives
badly; do not alias a unary RPC the generated stub already exposes) rather than the older sketch
this replaces, which predates that rule:

| RPC | shape | carries `transaction` | treatment |
|---|---|---|---|
| `TimeSeriesWriteStream` | client-streaming | no | facade wrapper, top-level only |
| `TimeSeriesQuery` | server-streaming | yes | facade wrapper **and** bound on the transaction handles |
| `TimeSeriesLatest` | unary | yes | bound on the handles; `raw` at top level |
| `TimeSeriesWrite` | unary | no | `raw` only, documented |

`TimeSeriesWriteStream` mirrors `insertStream` / `insert_stream`; `TimeSeriesQuery` mirrors
`streamQuery` / `stream_query`. `TimeSeriesWrite`'s exclusion from the handles is a different kind
of exclusion than `insertStream`'s: `insertStream` is missing from the handle because a server bug
(arcadedb#6607, since fixed) made its `TransactionContext` meaningless, whereas
`TimeSeriesWriteRequest` has no `transaction` field in the contract at all. The two have different
futures — the first could join the handles once nothing depends on remembering the bug; the second
cannot, short of a contract change.

**The HTTP write path is not a gap.** `POST /ts/{database}/write` takes a `text/plain`
line-protocol body and is one of the four pinned entries in Python's `EXPECTED_SKIPS`, because
`openapi-python-client` generates a full operation function per endpoint from the JSON contract
and drops any endpoint whose request body isn't JSON. But `arcadedb-driver`'s facade
(`facade/timeseries.py`) hand-writes `write` — a synchronous and an `Async` twin — on top of the
generated client's own pooled httpx client, so it shares connections, headers and timeout with
every generated call. `@arcadedb/driver` never had the gap to begin with: `openapi-typescript`
only emits types, not callable operations, so every method in its HTTP facade (`facade/*.ts`) is
hand-written regardless of a body's content type, and `writeTimeSeries` is one of them. gRPC
`TimeSeriesWrite` and `TimeSeriesWriteStream` give both languages a typed write path in addition
to the existing HTTP one, not instead of it.

The inference that produced the original error is worth stating plainly so it is not repeated: **a
skipped endpoint means the generator dropped it, not that a user cannot call it.**
`EXPECTED_SKIPS` answers the first question; only `facade/` answers the second.

#### Precision disagrees across transports

The two transports disagree about what an omitted `precision` means, and the disagreement is
silent on both sides:

| transport | omitted `precision` means | why |
|---|---|---|
| HTTP `POST /ts/{database}/write` | nanoseconds | documented default on the query parameter |
| gRPC `TimeSeriesWriteRequest.precision` | milliseconds | proto3 zero value is `TS_PRECISION_MILLISECONDS = 0` |

A caller porting a working HTTP ingest to gRPC and dropping the argument misreads every timestamp
by a factor of 10⁶, with no error on either side: proto3 cannot distinguish "omitted" from
"explicitly milliseconds" on a non-`optional` enum field, so the client cannot detect the mistake
either. This is why M6's wrappers make `precision` a required argument in both languages rather
than an optional one with a default — the failure is removed by construction instead of documented
and hoped against.

Prometheus remote `read` and `write` (`POST /ts/{database}/prom/read` and `/prom/write`,
`application/x-protobuf`) are what remain genuinely unwrapped in both languages; M6 does not touch
them.

### M7 — HTTP ndjson streaming for query and command (arcadedb#7306)

> **Corrected 2026-09-12** (`ArcadeData/arcadedb-drivers#39`): this section originally claimed
> neither generated layer could express a streamed response — that `openapi-fetch` buffers the
> response and `openapi-python-client` parses it whole — and treated a hand-written transport
> sitting *beside* the generated client, sharing its base URL, auth and error mapping "by
> discipline", as the milestone's central requirement. Both halves are wrong, and the section
> below replaces the original text rather than annotating it; see the M7 plan and issue #39 for
> how the error was found.

M7 adds ndjson streaming for `/query` and `/command` to both HTTP clients. What it adds is a
**transform** — bytes to lines to `NdJsonQueryEvent` to an async iterable — not a transport. Both
generated layers already expose a streaming primitive; the milestone rides it instead of building
a second one:

| Original claim | What is actually true | Checked by |
|---|---|---|
| `openapi-fetch` buffers the whole response; it cannot stream | `openapi-fetch@0.17.0` accepts `parseAs: "stream"` and, on a 2xx response, returns `response.body` — the raw `ReadableStream` — unparsed | `grep -n 'parseAs === "stream"' typescript/node_modules/openapi-fetch/dist/index.mjs` → line 185, `return response.body;` |
| `openapi-python-client` parses the response whole; it cannot stream | Its generated `Client`/`AsyncClient` hand out the pooled `httpx.Client`/`httpx.AsyncClient` they wrap via `get_httpx_client()`/`get_async_httpx_client()`, and both are real `httpx` clients with a `.stream()` method | `Client(base_url=...).get_httpx_client()` and `.get_async_httpx_client()`: both `hasattr(obj, "stream")` is `True` |
| A streaming path must share base URL, auth and error mapping with the generated client "by discipline", because it lives beside it | `openapi-fetch` handles a non-ok response the same way regardless of `parseAs`: it always reads the body as text and JSON-parses it into `{ error, response }`. `unwrap()` and `ArcadeDBError` need no change for the streaming path | Same file, ~line 195: the `response.ok` branch is the only place `parseAs` is consulted; the error branch below it is unconditional |

**The risk the old text named cannot occur.** It named two ways to authenticate, or two ways to
raise, as the defect this milestone was most likely to introduce — a real risk *if* a second
transport existed to drift from the first. None does: `queryStream`/`commandStream` and
`query_stream`/`command_stream` call through the same generated client `query`/`command` already
use, just with `parseAs: "stream"` (TypeScript) or `.stream()` on the same pooled `httpx` client
(Python). One transport per language means there is nothing else to hold a second way to
authenticate or a second way to raise, so that failure mode is not merely unlikely here — it has
no mechanism to occur through.

**Batch stays out, tracked separately as #52.** `/batch` is entirely unwrapped in both clients
today — no facade method calls it at all. Adding batch streaming here would mean introducing the
endpoint itself, non-JSON request body and seventeen tuning query parameters included, rather than
adding a streaming mode to a wrapper that already exists for `query` and `command`. Upstream
tracks it separately too: batch's `Accept`-negotiated streaming is arcadedb#7311, distinct from
the #7306 streaming half this milestone covers.

- TypeScript: `openapi-fetch`'s own `parseAs: "stream"`, decoded line-by-line and surfaced as an
  `AsyncIterable`.
- Python: the generated client's pooled `httpx.Client`/`AsyncClient`, `.stream()` with
  line splitting hand-rolled over `iter_text()`/`aiter_text()`, synchronous and asynchronous.
  **Not** `iter_lines()`: its `LineDecoder` splits on `str.splitlines()` semantics, which include
  U+0085, U+2028 and U+2029 — all legal raw characters inside a JSON string that the server does
  not escape — so a record carrying one is split mid-JSON and surfaces as a bare
  `json.JSONDecodeError` partway through the stream. `iter_text()` still runs httpx's own
  incremental decoder, so only the line splitting is hand-written, not the UTF-8 decoding.
- Surface: `queryStream` / `commandStream`, `query_stream` / `command_stream`.

This milestone rests on four decisions worth naming, because later tasks cite them by ID:

- **D-M7-1** — ride the generated client's own streaming primitive rather than a hand-written
  transport beside it. This is the corrected premise itself: with one transport per language,
  there is nothing for a second transport's auth or error handling to drift from.
- **D-M7-2** — the stream yields an `NdJsonQueryEvent` union (`record`, `stats`, `error`), not a
  bare row. A `record`-only stream would silently drop the `stats` trailer — `limit`, `returned`,
  `truncated` — the same information the buffered response cannot afford to drop either.
- **D-M7-3** — an in-band `error` event raises `ArcadeDBError`. It is a failure the server raised
  *after* the `200` was already written; the status line cannot be withdrawn once bytes are
  flowing, so the failure arrives in the body instead. Raising the same exception type the
  buffered path raises keeps the two paths failing alike.
- **D-M7-4** — the buffered `query`/`command` are untouched: still no `Accept` header, still a
  `QueryResponse`, byte-identical to before this milestone. Streaming is additive.

M4's D6 narrowing helper becomes the real discriminator here.

### M8 — Control plane, reachable then documented (arcadedb#7308, #7309, #7310)

> **Corrected 2026-09-12** (`ArcadeData/arcadedb-drivers#40`): this section originally said the
> control-plane RPCs "stay reachable on `raw` / the stub" and that the milestone's deliverable was
> a README section enumerating them as such. Neither half holds — `ArcadeDbAdminService` is
> reachable through neither client's public API today. The section below replaces the original
> text rather than annotating it; see issue #40 for how the error was found.

**The admin service is not reachable today, in either language.** `ArcadeDbAdminService` appears
nowhere outside generated code in either package (`grep -rn 'AdminService'
typescript/packages/driver-grpc/src python/packages/driver-grpc/src/arcadedb_driver_grpc
--include='*.ts' --include='*.py' | grep -vE '/gen/|_generated'` prints nothing), and `raw` is
bound to the **data-plane** service in both: `ArcadeDbServiceStub(channel)` in Python,
`createClient(ArcadeDbService, transport)` in TypeScript. Reaching the admin stub today costs
differently in each language, and the difference is the point:

| | what reaching `ArcadeDbAdminService` costs today |
|---|---|
| Python | impossible through the public API — the only path is `client._channel` paired with `arcadedb_driver_grpc._generated.arcadedb_server_pb2_grpc`, both private names |
| TypeScript | the service descriptor is exported by the blanket `export *`, but the transport `createClient` binds it to is a local `const`; a caller must build a second transport of their own with `createGrpcTransport(...)` — which **bypasses the refusal to pair a plaintext-password interceptor with a non-TLS `baseUrl`**, the guard added for arcadedb#5048 |

The TypeScript cost is the one that matters. Documenting it as the way to reach the admin
service — which is what the original section asked for — would mean publishing instructions for
defeating a credential-exposure control, on a service whose `CreateApiToken` returns secret
material. That is the opposite of what M8 should ship.

**So M8 exposes the stub once per package, instead of only documenting a path around it.** A new
`rawAdmin` (TypeScript) / `raw_admin` (Python) is built from the same transport or channel that
`raw` / `self.raw` already uses. Because there is exactly one transport, or channel, per client —
not two — auth and the arcadedb#5048 insecure-channel refusal apply to the control plane for the
same reason they already apply to the data plane: there is nothing else for a second admin
transport to disagree with, not because M8 reimplements either guard.

**This does not breach the parity bar (§3, D4).** D4 keeps unary control-plane RPCs off the facade
because a facade over a one-line stub call would add a name and nothing else; it says nothing
about whether the stub is reachable in the first place. Exposing `rawAdmin` / `raw_admin` is
exactly what `raw` / `self.raw` already does for the data plane — the client hands out a stub
already bound to its transport, once, not a facade over forty-four RPCs. Every admin RPC is still
called exactly as D4 describes: `client.rawAdmin.health({})`, not a hand-written `client.health()`.

**`Health` and `Ready` get no facade — the empty request is why.** Both request messages are empty
in the contract (`message HealthRequest {}`, `message ReadyRequest {}`), so the entire difference
between the stub call and a hypothetical facade method is `rawAdmin.health({})` versus `health()`.
An empty request makes these the *easiest* RPCs to call through a bare stub, not the hardest — the
opposite of what an exception to D4 would need. The original section had this backwards, naming
`Health`/`Ready` as "the one pair worth facading despite D4"; the empty request is exactly why they
are the weakest candidate for an exception, not the strongest.

**The corrected count.** `ArcadeDbAdminService` carries 44 RPCs, not the 32 this section originally
cited: 41 unary and 3 server-streaming (`RestoreBackup`, `RestoreDatabase`, `ImportDatabase` —
server-streaming precisely so a long restore reports progress and stays cancellable, per §2.2). Of
the 41 unary RPCs, 32 were new in the 26.10.1 contract (§2.2's list) and nine pre-date it (`Ping`,
`GetServerInfo`, `ListDatabases`, `ExistsDatabase`, `CreateDatabase`, `DropDatabase`,
`GetDatabaseInfo`, `CreateUser`, `DeleteUser`) — which is what reconciles with the "32" this
section used to give as the service's whole size: that number was always §2.2's count of what was
*new*, not the service's actual RPC count.

The deliverable is `rawAdmin` / `raw_admin` plus a README section per gRPC package enumerating what
is now callable through it. The enumeration is machine-checked against the generated stub's own
method set rather than hand-maintained, so a list of 44 names cannot silently fall behind the next
contract bump — the same failure mode `check_codegen_skips.py` exists to catch on the HTTP side.

One thing this milestone must still prove rather than assume: **`CreateApiToken` returns secret
material.** arcadedb#7309 makes the server-side argument that a token-bearing response must be
proved not to reach a log sink. The client side owes the same proof — that no interceptor or
middleware in either package touches a response body, and a README line saying so. If any does,
that is a finding, not a documentation task.

## 7. Risks

**The SNAPSHOT moves daily.** M4 may need a re-fetch before it merges. The mitigation is to merge
M4 quickly rather than to pin anything: once it is in, `contract-watch.yml` resumes against the
adopted version and any further movement is reported the normal way.

**A widened skip set would pass unnoticed.** This is the failure mode `check_codegen_skips.py`
exists for, and M4 step 4 is the only place in this plan where the right response to a green-ish
signal is to stop. Called out here so it is not treated as a formality.

**A later change could reintroduce a second transport.** M7's one-transport-per-language property
(§4 M7, D-M7-1) holds only as long as every caller reaches for the generated client's own
streaming primitive — `parseAs: "stream"` in TypeScript, the pooled `httpx` client's `.stream()`
in Python — instead of building a fresh one. A contributor who doesn't know either exists and
reaches for a hand-rolled `fetch` or a new `httpx.Client()` would reopen the two-contracts risk M7
was designed, by construction, to avoid.
